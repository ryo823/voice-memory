現行の FPR（1件以上返したら誤検出）は、全件を順位付けして返す C・D では構造的に 1.0 になる。以下は C の類似度に固定閾値を当てた参考値で、**閾値を評価セットに合わせて調整はしていない**（0.80 / 0.85 は指示された値のみ）。クエリ10件・正解あり54件と標本が小さく、閾値の最適化に使える精度ではない。

## 方式Eの判断: 実施しない

D の R@5=0.933 に対して R@10=0.988 で、差は 0.055。「正解が top10 に入るが top5 に入らない」クエリは次の6件だけで、リランクで改善できる見込みが乏しい。

| クエリ | 正解数 | D の R@5 → R@10 | 評価 |

| q20 健康（tag） | 8 | 0.250 → 0.375 | 語としてタグ名に当たるかの問題で、意味的な順位付けの弱さではない |

基準: ① 全体 R@5 が A 比 +0.15 以上（≥0.581）／② exact・short が A 比 0.05 を超えて悪化しない／③ no_match 誤検出が 3/10 以下／④ 平均応答 1 秒未満

## 最終推奨

**D（B + C のハイブリッド）を第3週以降の検索基盤の本命とするが、「無条件採用」ではなく、次の条件が揃ってから採用する（条件付き採用）。**

- 選ぶ理由: D は R@5=0.933 / R@10=0.988 で最も高く、語彙一致（person_event・composite・exact）と意味検索（paraphrase・temporal）の両方を保つ。C 単独は composite（0.600）と tag（0.406）が弱く、B 系は paraphrase（0.533）を拾えない。応答は 8ms 程度で基準に大きく余裕がある。
- **条件1: 棄却の仕組みが別途必要。** 閾値だけでは分けられない（上記）。B の語彙一致の有無・C と B の合意・相対スコア（top1 と次点の差）などを組み合わせた棄却を設計し、評価する。今回の閾値分析は「分離できない」ことの確認までで、有望な方式の評価はしていない。基準③は「全件返す方式の FPR」ではなく、棄却後の結果で再判定する。FPR の定義（1件以上返したら誤検出）自体も、ベクトル系では「上位に出しても正解でないものを示すか」に見直す余地がある。
- **条件2: ruri の第三者変換 ONNX の確認。** 配布元 `sirasagi62/ruri-v3-30m-ONNX` は公式配布ではない。ライセンス（本家 ruri-v3 のモデルカードで要確認）と、本家 PyTorch モデルとの出力一致（同一入力でのコサイン類似度の差）を確認してから本番に入れる。量子化 int8 は fp32 と同等という結果はスパイクで得たが、文書バッチの組み方で値が微妙に変わる（今回、文書の並び順を固定して再現性を確保した）。
- **条件3: 時間表現の扱い。** temporal の MRR は 0.68 止まり（月の違うメモが混ざる）。「十一月」「先月」などは検索語ではなく `recorded_at` の絞り込みとして処理する（Run1 の提案どおり）。q31・q54 の失敗はこれ。
- **条件4: tag の扱い。** C 単独の tag は R@5=0.406 / R@10=0.594 と弱い。D で 0.719 / 0.844 まで戻るが A の 0.812 / 1.000 には届かない。タグ名の完全一致は別系統（タグ指定での絞り込み）として残すのが安全。
- 運用面: C はモデルロード 0.5 秒・RSS 約250MB（スパイク値）が常駐コストになる。Raspberry Pi 5 での常駐サーバ構成とメモリ予算は未検討。文書埋め込みは保存時に計算してDBに持つ設計が必要（今回はキャッシュのみ）。
- B2 は B の一般的な改善（tag の悪化が解消、他は無変化）なので、D に組み込む B は B2 に差し替えて再測定する価値がある（今回の D は指示どおり素の B）。
- 限界: 評価セットは合成120件・クエリ64件で、no_match は10件のみ。数値の差のうち小さなもの（B2 の +0.012、D と C の差など）は有意とは言えない。
